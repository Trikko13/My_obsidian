
### Раздел 1: Основные концепции и философия ClickHouse

**Вопрос 1: Что такое ClickHouse и в чем его основная философия?**

**Ответ:** ClickHouse — это колоночная OLAP-СУБД с открытым исходным кодом, разработанная в Яндексе для выполнения аналитических запросов в реальном времени над большими объемами данных.

**Ключевая философия:** "Быстрые запросы на большом объеме данных любой ценой". Это достигается за счет:

- **Колоночное хранение:** Данные хранятся по столбцам, что позволяет читать только необходимые для запроса столбцы, уменьшая I/O.
    
- **Векторное исполнение запросов:** Обработка данных происходит не по одной строке, а блоками (векторами), что значительно лучше использует CPU.
    
- **Аппаратная оптимизация:** Максимальное использование возможностей CPU, RAM и дисков.
    

**Вопрос 2: В чем разница между OLTP и OLAP? И почему ClickHouse — это OLAP?**

**Ответ:**

- **OLTP (Online Transaction Processing):** Системы для частых коротких операций записи/чтения (например, интернет-магазин). Акцент на целостность данных, транзакционность. Примеры: PostgreSQL, MySQL.
    
- **OLAP (Online Analytical Processing):** Системы для сложных аналитических запросов на больших объемах данных, в основном чтение. Акцент на скорость агрегации. ClickHouse — типичный представитель OLAP.
    

**Нюанс:** ClickHouse не является заменой OLTP-базам. Он плохо подходит для частых точечных UPDATE/DELETE.

### Раздел 2: Ключевые термины и архитектура

**Вопрос 3: Что такое Движки (Engines) таблиц? Какие основные виды вы знаете?**

**Ответ:** Движки таблиц в ClickHouse определяют, как и где хранятся данные, их репликация и шардирование.

- **Семейство `MergeTree`:** Наиболее важные и мощные движки. Позволяют индексировать данные, указывать ключ сортировки и партиционирование.
    
    - `ReplicatedMergeTree`: Надстройка над `MergeTree` для обеспечения репликации данных между узлами кластера.
        
- **Лог-движки (`StripeLog`, `TinyLog`):** Простые движки для быстрой записи небольших объемов данных (логи, стриминг). Неэффективны для больших данных и сложных запросов.
    
- **Движки для интеграции:** Позволяют работать с внешними данными "на лету" (например, `MySQL`, `PostgreSQL`, `S3`, `Kafka`).
    

**Вопрос 4: Что такое `MergeTree`? Объясните его основные концепции.**

**Ответ:** `MergeTree` — это движок для хранения больших данных с поддержкой индексов.

**Ключевые концепции:**

1. **Первичный ключ (Primary Key):** Определяет, как данные будут отсортированы на диске. _Не гарантирует уникальности._ Используется для быстрого поиска по диапазону.
    
2. **Ключ партиционирования (Partition Key):** Определяет, как данные разбиваются на логические части (партиции). Это ускоряет запросы, которые затрагивают только определенные партиции, и упрощает управление данными (например, удаление старых данных по партиции).
    
3. **Индекс засечек (Primary Index):** Разреженный индекс, построенный по первичному ключу. Он хранит каждую N-ю засечку (по умолчанию 8192). Позволяет быстро найти нужные блоки данных.
    
4. **Фоновые мержи (Merges):** Процесс, в котором маленькие кусочки данных (куски) объединяются в более крупные для оптимизации чтения.
    

**Нюанс:** Порядок столбцов в первичном ключе критически важен для эффективности запросов. Запросы с условиями по первому столбцу ключа работают максимально эффективно.

**Вопрос 5: Что такое шардирование и репликация в контексте ClickHouse?**

**Ответ:**

- **Шардирование (Sharding):** Горизонтальное партиционирование данных. Разные части данных (шарды) хранятся на разных серверах. Это нужно для масштабирования.
    
- **Репликация (Replication):** Создание копий данных на разных серверах. Это нужно для отказоустойчивости и распределения нагрузки на чтение.
    

**Как это работает в ClickHouse:** Используются **кластерные таблицы**. Вы создаете распределенную таблицу (например, `distributed_table`), которая сама данных не хранит, а является "виртуальным" представлением поверх локальных таблиц на шардах (например, `local_table`). Запрос к `distributed_table` рассылается на все шарды, агрегирует результаты и возвращает клиенту.

### Раздел 3: Нюансы и оптимизация

**Вопрос 6: Как ClickHouse обрабатывает `JOIN`? В чем его особенность?**

**Ответ:** ClickHouse не реляционная СУБД, и `JOIN` — не его сильная сторона.

**Особенности:**

- Все JOIN'ы — **INNER** или **LEFT**.
    
- ClickHouse использует стратегию **"Все-в-память" (In-memory hash join)**: правая таблица (subquery) полностью читается в оперативную память и строится хеш-таблица. Поэтому очень важно, чтобы "правая" таблица была небольшой.
    
- Не рекомендуется использовать JOIN'ы для больших таблиц "лоба-в-лоб". Часто данные денормализуют (хранят в одной широкой таблице) для избежания JOIN'ов.
    

**Вопрос 7: Как можно обновлять или удалять данные в ClickHouse?**

**Ответ:** Это один из самых частых вопросов, так как ClickHouse не поддерживает классические UPDATE/DELETE в OLTP-стиле.

- **Мутации (Mutations):** Это асинхронные операции `ALTER TABLE ... UPDATE/DELETE`. Они не транзакционны, выполняются в фоне и могут быть долгими, так как перезаписывают целые куски данных.
    
- **С помощью партиционирования:** Самый эффективный способ "удаления" — отцепление партиции (`ALTER TABLE ... DETACH PARTITION`).
    
- **CollapsingMergeTree / ReplacingMergeTree:** Специальные движки для обработки "изменяющихся" данных. Они требуют специального подхода (версионность, сортировка) и не гарантируют консистентность на 100% без финального агрегирующего запроса с `FINAL`.
    

**Вопрос 8: Какие типы данных наиболее эффективны в ClickHouse?**

**Ответ:**

- Используйте **малоразмерные типы**: `UInt8`, `Int32`, `Float32` вместо их 64-битных аналогов, если это позволяет домен данных.
    
- **`LowCardinality`** для строковых полей с небольшим количеством уникальных значений (например, статусы, коды стран). Экономит память и ускоряет группировки.
    
- **`Nullable`** типы имеют накладные расходы. Старайтесь избегать их, используя значения по умолчанию (например, 0 или пустая строка).
    

**Вопрос 9: На что стоит обращать внимание при проектировании таблицы?**

**Ответ:**

1. **Порядок столбцов в первичном ключе:** От самого селективного к наименее селективному.
    
2. **Партиционирование:** Выбирайте такой ключ, чтобы партиции были не слишком мелкими (сотни-тысячи) и не слишком крупными. Идеально — разбивать по дате (например, `toYYYYMM(event_date)`).
    
3. **Избегайте излишней гранулярности:** Не включайте в первичный ключ столбцы, которые редко используются в WHERE.
    
4. **Используйте кодекы сжатия:** Например, `CODEC(DoubleDelta, LZ4)` для временных рядов.

### Раздел 4: Практические вопросы

**Вопрос 10: Как вы будете мониторить производительность ClickHouse?**

**Ответ:**

- **Системные таблицы:** `system.query_log`, `system.part_log`, `system.metrics`, `system.events`.
    
- **Анализ медленных запросов:** Смотреть в `query_log` на запросы с большим `query_duration_ms`.
    
- **Профилировщик:** Включить `SET send_logs_level='trace'` и посмотреть лог выполнения запроса, чтобы увидеть, сколько строк было прочитано и отфильтровано на каждом этапе.
    
- **EXPLAIN PIPELINE:** Показывает, как выполняется запрос на уровне процессорных конвейеров.
    

**Бонусный вопрос: Когда НЕ стоит использовать ClickHouse?**

**Ответ:** ClickHouse — не панацея. Его не стоит использовать, когда:

- Нужны частые точечные UPDATE/DELETE (OLTP-сценарий).
    
- Требуются транзакции и строгая консистентность ACID.
    
- Высокие требования к одновременной записи (хотя с буферизацией и Kafka-интеграцией это решаемо).
    
- Много сложных JOIN'ов между большими таблицами.

Шаг-за-шагом: список типовых вопросов с краткими опорными тезисами

1. Архитектура и модель данных  
    — Что такое «часть таблицы» (part), гранула (mark / granularity) и как идут слияния (merge)?  
    Ключ: вставка формирует парты, фоновые мерджи объединяют; гранула — минимальная порция чтения по индексу.
    
2. Семейство MergeTree: базовый MergeTree и производные  
    — Когда выбирать MergeTree, ReplacingMergeTree, SummingMergeTree, AggregatingMergeTree, Collapsing/VersionedCollapsing?  
    Ключ: Replacing — устранение дубликатов по version; Summing — агрегация чисел по ключу; Aggregating — хранит состояния агрегатов; Collapsing — свёртка +1/−1; VersionedCollapsing — с версией.
    
3. ORDER BY vs PRIMARY KEY  
    — В чём разница?  
    Ключ: ORDER BY задаёт порядок на диске; PRIMARY KEY — разреженный индекс для пропуска чтения. Если PK не указан — равен ORDER BY.
    
4. Партиционирование  
    — Зачем PARTITION BY и чем отличается от ORDER BY? Как выбирать ключ партиции?  
    Ключ: партиция — крупная «папка» частей для управления (DROP/ATTACH/REPLACE), ограничение скана; берём по дате/логическому разрезу.
    
5. Индексы-пропуски (data skipping)  
    — Какие бывают: minmax (встроенный), bloom_filter, set, ngram/token bloom. Когда полезны?  
    Ключ: ускоряют отбор по столбцам с селективными предикатами; работают на уровне гранул.
    
6. LowCardinality и кодеки сжатия  
    — Когда использовать LowCardinality? Какие кодеки: LZ4, ZSTD, Delta/DoubleDelta, Gorilla, T64 и их комбинации?  
    Ключ: LowCardinality для строк с невысоким кардиналитетом; Delta/DoubleDelta/Gorilla эффективны для монотонных/временных/числовых рядов.
    
7. Вставка данных и батчи  
    — Почему лучше писать крупными батчами? Что такое async inserts/накопление, дедупликация вставок?  
    Ключ: большие блоки уменьшают число частей и нагрузку на мерджи; можно включать async insert; дедуп по insert_deduplication_token.
    
8. Репликация и шардинг  
    — ReplicatedMergeTree: роль ZooKeeper/ClickHouse Keeper; чем отличаются репликация и шардинг?  
    Ключ: репликация — копии одних и тех же партиций; шардинг — горизонтальный разрез; часто используются вместе.
    
9. Distributed-движок  
    — Как работает Distributed, что такое шард/реплика, шард-ключ? Что делает prefer_localhost, internal_replication?  
    Ключ: маршрутизация запросов по шардам; шард-ключ распределяет вставки; настройками управляем чтением локально и поведение реплик.
    
10. Кворумы и согласованность  
    — Что такое insert_quorum, select_sequential_consistency, max_replica_delay_for_distributed_queries?  
    Ключ: кворум повышает гарантию доставки на N реплик; контроль отставания реплик при чтении.
    
11. JOIN’ы в ClickHouse  
    — Типы: ANY/ALL/SEMI/ANTI/ASOF. Алгоритмы: hash/partial_merge/grace_hash (auto). Когда какой?  
    Ключ: большие нерешающие ключи — grace/partial merge; в памяти — hash. ANY — как left semi-dedupe справа; ASOF — по ближайшему по времени.
    
12. Материализованные представления и проекции  
    — Разница между VIEW, MATERIALIZED VIEW (TO таблица), POPULATE; когда это лучше, чем «агрегирующие таблицы»/проекции?  
    Ключ: MV — потоковая денормализация/агрегация при INSERT; проекции — внутренняя оптимизация чтения предопределённого плана.
    
13. Словари (Dictionaries)  
    — Источники (файл, HTTP, БД), режимы (cache, direct, ssd_cache), зачем использовать?  
    Ключ: быстрый lookup измерений без JOIN тяжёлой таблицы; control обновлений и TTL словаря.
    
14. TTL, storage policies и иерархия дисков  
    — Как задать TTL на строки/столбцы, перенос между volume/disk и удаление?  
    Ключ: политика хранения (HDD/SSD) + TTL MOVE/DELETE; автоматическое охлаждение данных.
    
15. Мутации: UPDATE/DELETE  
    — Почему «дорого»? Как отслеживать в system.mutations? Что такое lightweight delete?  
    Ключ: постфактум переписывание частей; асинхронно; мониторинг статуса мутаций; лёгкие delete-метки оптимальнее для частых удалений.
    
16. Профилирование и план  
    — EXPLAIN AST/PLAN/PIPELINE, system.query_log/query_thread_log, system.parts/merges/part_log. Что смотреть в первую очередь?  
    Ключ: план/пайплайн для операторов и стадий, логи для времени и аллокаций, parts — объём и фрагментация.
    
17. Настройки производительности  
    — max_threads, max_memory_usage, max_bytes_before_external_{sort,group_by}, allow_experimental_{...}. Когда включается «внешняя» сортировка/группировка?  
    Ключ: при превышении порогов — пролив на диск; аккуратно с лимитами памяти и числом потоков.
    
18. Частые паттерны моделирования  
    — Денормализация vs MV + AggregatingMergeTree; «широкие» таблицы; партиционирование по дате; стабильный ORDER BY (date, key).  
    Ключ: ориентируемся на чтение/скан; минимизируем рандом-доступ; стабильная сортировка для пропусков.
    
19. Частые грабли  
    — ORDER BY «не по селективным полям», микробатчи вставок → много мелких parts, cartesian JOIN, UPDATE/DELETE на массив данных, отсутствие фильтра по партиции.  
    Ключ: следить за parts, гранулярностью, селективностью ключа, фильтрами по PARTITION.
    
20. Безопасность и управление доступом  
    — Роли/профили/квоты (RBAC), row-level security (policies), audit в system.query_log.  
    Ключ: CREATE USER/ROLE/GRANT; квоты по ресурсам и времени.
    
21. Резервные копии и восстановление  
    — BACKUP/RESTORE, куда копируем (локально/S3), консистентность при репликации.  
    Ключ: бэкап на уровне таблиц/БД/кластера; учитывать размер и время остановки вставок.
    
22. Интеграции и источники стриминга  
    — Kafka-движок, RabbitMQ, S3, MySQL/PostgreSQL репликации (MaterializedMySQL/…); когда что выбирать.  
    Ключ: Kafka → буферная таблица + MV в MergeTree; для внешних БД — материалы/движки-адаптеры.
